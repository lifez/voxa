# Voxa response-time benchmark — 2026-09-27

## ขอบเขต

วัดบน Linux Omarchy x86_64, kernel 7.2.5-3, Node v26.8.2, Python 3.14.7 เครื่องเดียว ไม่มีการ restart/install service หรือแก้ keybindings การทดสอบใหม่ใช้ `status` กับ daemon จริง และเปิด default microphone ชั่วคราวเพื่อจับเวลาถึง PCM ชุดแรกเท่านั้น ไม่เก็บเสียง ไม่ส่งเสียงเข้า API ไม่สั่ง paste ไม่อ่าน/เปลี่ยน clipboard

ตัวเลข transcription/paste มาจาก journal การใช้งานจริง ไม่ใช่การ replay เสียงควบคุม และ service ที่ติดตั้งอยู่เป็นคนละ snapshot กับ source ปัจจุบัน (เช่น log การหยุดอัดต่างกัน) จึงห้ามนำผลนี้ไปอ้างเป็นผล end-to-end ของ source ที่แก้ใหม่

## 1. ผลเดิมที่รายงาน

หน่วย ms; P95 ใช้ nearest rank

| ขั้นตอน | ค่ากลางที่รายงาน | P95 | N | วิธี |
|---|---:|---:|---:|---|
| CLI `status` รวมเริ่ม Node | 42.6 | 45.2 | 30 | วัดใหม่ subprocess |
| socket `status` โดยตรง | 0.1 | 0.2 | 50 | วัดใหม่ใน process เดียว |
| เริ่ม mic → PCM ชุดแรก | 171.2 | 209.3 | 6 | default device, pw-record 100ms |
| log หยุดอัด → transcript | 398 | 444 | 23 | journal วันนี้ |
| transcript → paste command เสร็จ | 13.4 | 15.5 | 18 | ส่วนต่าง timestamp journal |
| log หยุดอัด → paste command เสร็จ | 425.5 | 514.7 | 18 | ส่วนต่าง timestamp journal |

หมายเหตุ: สคริปต์รอบแรกของการวัดใหม่ใช้ lower middle เมื่อ N เป็นเลขคู่ ไม่ได้เฉลี่ยสองค่ากลาง ส่วน journal ใช้ median มาตรฐาน ตารางนี้เก็บตัวเลขเดิมโดยไม่แก้ย้อนหลัง

- 23 transcripts รวม 5 ครั้งที่ว่าง; 18 ครั้งมีการ paste ส่วนรอบ error ไม่รวมใน latency ที่สำเร็จ
- เวลาถอดเสียงเป็นค่าที่ application log ไว้ ส่วน paste เป็นการประมาณจาก journal timestamp ซึ่งอาจมี scheduling/buffering ของ log
- ไม่วัด keyboard event → CLI, OSD render หรือข้อความปรากฏจริงในแอปปลายทาง
- เวลาที่พูดไม่ใช่ response time และไม่ได้รวมใน stop→paste
- ห้ามบวก median แต่ละแถวเพื่ออ้างว่าเป็น median รวม เพราะมาจากคนละ distribution/sample
- P95 ที่มี sample น้อยยังไม่ใช่ SLA หรือผลรับรองระยะยาว

## 2. ทดลอง optimization และภาษาอื่น

### วิธี

ใช้ client ทุกตัวส่ง `status\n` ไปยัง daemon เดียวกัน วัดด้วย Python `perf_counter_ns` ตั้งแต่เริ่ม subprocess จน exit รวมรันไทม์/import/socket/output ฝั่ง client ไม่รวม compiler

แต่ละตัว warmup 5 ครั้ง แล้ววัด 100 ครั้งต่อ implementation สลับลำดับในแต่ละรอบด้วย seed 42; filesystem cache อุ่น ไม่ใช่ cold boot ไม่มีโหลดจำลองเพิ่มเติม

Baseline ใช้สำเนา `dist/` ก่อน build การแก้ครั้งนี้ ซึ่งวัดได้สอดคล้องกับผล CLI เดิม

| Client | Median ms | P95 ms | เทียบ baseline median |
|---|---:|---:|---:|
| Node เดิม eager imports | 42.10 | 44.10 | baseline |
| Node lazy imports | 21.99 | 24.39 | ลด ~48% |
| Python prototype | 11.93 | 12.43 | ลด ~72% |
| C prototype (`cc -O2`) | 0.64 | 0.75 | ลด ~98.5% |

Raw summary: [control-2026-09-27.json](control-2026-09-27.json)

### สิ่งที่แก้จริง

- `src/runtime.ts`: แยก socket path ออกจาก daemon เพื่อไม่ต้องโหลด audio, WebSocket, config/setup ในคำสั่งควบคุม
- `src/index.ts`: lazy-load เฉพาะ dependency ของคำสั่งที่ใช้; `start/stop/toggle/status` เหลือเส้นทางเบา
- `src/daemon.ts`: ใช้ runtime module ร่วมกันและ re-export API เดิม
- `bench/control.py`, `bench/control.c`: prototype control client รองรับสี่คำสั่ง ไม่ใช่การ rewrite transcription daemon ทั้งระบบ
- `test/control-cli.test.mjs`: ใช้ mock socket ตรวจ protocol ทั้งสาม client รวม invalid command และ missing daemon; ไม่ส่งคำสั่งอัดไป service จริง

**ข้อสรุป:** เปลี่ยนเฉพาะ client คุ้มกว่าการ rewrite ทั้งระบบเพื่อแก้เวลาเริ่ม Node การใช้ C อาจประหยัด ~41ms ต่อการเรียกเมื่อเทียบ baseline แต่ผล `status` เป็น proxy ไม่ใช่หลักฐานว่าปล่อยปุ่ม→paste จะลดเท่ากัน ขณะที่ Python ยังมี startup overhead และเพิ่ม runtime dependency ส่วน C เพิ่มภาระ build/distribution/security review

ยังไม่ได้ติดตั้ง C/Python หรือ Node เวอร์ชันแก้ใหม่เข้า service จริง ไม่ได้เปลี่ยน keybindings และไม่ได้พิสูจน์บน macOS

## 3. ทดลอง PipeWire latency

เปลี่ยนเฉพาะ `pw-record --latency` ใน benchmark ไม่เปลี่ยนค่า production วัด default device, 10 ครั้งต่อค่า สลับลำดับแบบหมุนเวียน ไม่มี warmup เปิดไมค์จนได้รับ PCM ครั้งแรกแล้วหยุดทันที ข้อมูลเสียงทิ้งทั้งหมด

| Requested latency | First PCM median | First PCM P95 | Stop→process close median |
|---|---:|---:|---:|
| 100ms (ปัจจุบัน) | 169.55ms | 170.66ms | 1.11ms |
| 50ms | 149.33ms | 179.42ms | 1.12ms |
| 20ms | 168.83ms | 193.61ms | 1.12ms |

Raw summary: [mic-2026-09-27.json](mic-2026-09-27.json)

50ms ลด median ~20ms แต่ P95 แย่ลงใน sample นี้ และ 20ms ไม่ได้เร็วกว่าอย่างชัดเจน Requested latency ไม่ใช่เวลาที่รับประกันโดยอุปกรณ์/graph จึง **ยังไม่เปลี่ยน default** ต้องทดลองซ้ำพร้อมพูดจริง ตรวจเสียงต้นประโยคหลุด, underrun, CPU และความแม่นยำการถอดเสียง Stop→close จากการอัดสั้นนี้ไม่ใช่หลักฐานเรื่อง drain หลังพูดยาว

## 4. จุดที่ควร improve ต่อ เรียงตามลำดับ

### A. ใช้ lazy CLI ก่อน — ทำแล้วใน source

ผลวัดชัดเจน ความเสี่ยงต่ำ ไม่เปลี่ยน audio/transcription pipeline ทดสอบผ่าน 15 tests, skipped 2 tests เฉพาะ macOS

### B. เพิ่ม instrumentation ก่อนปรับ transcription

เก็บ monotonic timestamps ต่อ session โดยไม่เก็บ transcript/key/audio:

1. command accepted
2. mic spawn และ first PCM
3. WebSocket open และ `session_started`
4. first audio send
5. stop requested และ mic drained
6. commit queued และ send callback (ไม่ใช่หลักฐานว่า server รับแล้ว)
7. committed transcript received
8. clipboard command exit และ paste command exit

เก็บ duration/จำนวน byte/error code แบบไม่เผยข้อมูลส่วนตัว แยก success, empty, error, recording duration และ cold/warm connection จึงจะรู้ว่า ~398ms มาจาก drain, network หรือ server processing เท่าไร

### C. Native control client — มี prototype พร้อมเปรียบเทียบ

ถ้าต้องการลดอีก ~21ms จาก Node ที่ optimize แล้ว ใช้ native binary เฉพาะ start/stop/toggle/status โดยคง Node daemon/setup ไว้ ควรเพิ่ม CI สำหรับ Linux/macOS, timeout/partial-response tests และ installer/fallback ก่อน deploy Rust/Go เป็นทางเลือกด้าน maintainability แต่เครื่องนี้ไม่มี toolchain จึงยังไม่มีผลวัดและไม่อ้างว่าเร็วกว่า C

### D. Audio frame size — ต้อง A/B ด้วยเสียงเดียวกัน

ปัจจุบันส่ง 200ms frame และเก็บ tail ประมาณ 200–400ms เพื่อ commit พร้อมเสียงจริง การลด frame/tail อาจทำให้เสียงถึง server เร็วขึ้นระหว่างพูด แต่เพิ่มจำนวน message, base64/JSON overhead และอาจกระทบข้อกำหนด API ต้องตรวจ API และ replay fixture เสียงที่ได้รับอนุญาต เปรียบเทียบ latency/error/accuracy ไม่ควรเปลี่ยนจากการคาดเดา

การ buffer นี้ไม่ได้บังคับรออีก 200ms หลังหยุด: โค้ดส่ง tail ทันทีเมื่อ commit ได้

### E. Connection reuse/preconnect — ประโยชน์ยังไม่พิสูจน์

WebSocket ปัจจุบันเปิดตอนเริ่มอัดพร้อมกับไมค์ จึงอาจซ้อนกับเวลาพูดอยู่แล้ว Preconnect อาจช่วยวลีสั้น แต่เพิ่ม connection idle, quota/ค่าใช้จ่าย และความซับซ้อนเรื่อง key rotation/config change ต้องตรวจ protocol/session lifetime ก่อน ไม่ควรเปิดไมค์ค้างเพื่อซ่อน startup เพราะผิดคุณสมบัติ no idle microphone capture

### F. ไม่ควรลด drain timeout แบบเดาสุ่ม

ใน source ปัจจุบัน 250ms เป็น **เพดาน** ของ `Promise.race`, ไม่ใช่ sleep คงที่ ถ้า capture ปิดใน ~1ms ก็เดินต่อได้ทันที ลด timeout อาจตัดเสียงท้ายโดยไม่ลดเวลาปกติ

### G. Paste path — ประโยชน์จำกัด

ปัจจุบัน ~13ms; direct clipboard/key injection หรือ helper ที่อยู่ถาวรอาจลด process spawn ได้ แต่เพิ่มภาระดูแล Wayland/permissions และอาจประหยัดน้อยกว่า CLI อย่างมาก ห้ามขนาน clipboard กับ Ctrl+V เพราะอาจ paste ข้อความเก่า

### H. Rewrite daemon ทั้งหมด — ยังไม่คุ้มจากข้อมูลนี้

ตัวเลขช่วง stop→transcript รวมการรอเครือข่าย/บริการภายนอก แต่ยังแยกส่วนไม่ได้ ไม่มี CPU profile ที่บอกว่า JavaScript เป็นคอขวด จึงยังไม่มีหลักฐานว่าเปลี่ยน daemon เป็น C/Rust/Go จะลด ~400ms ได้อย่างมีนัยสำคัญ ควรลงทุนกับ instrumentation และ controlled API benchmark ก่อน

## 5. ทำซ้ำ

ต้องมี daemon รันอยู่, Python 3, C compiler, Node และ dependencies:

```sh
npm run build
python3 bench/control-latency.py --runs 100
# เพิ่ม baseline ที่เก็บไว้พร้อม dependencies ของเดิม:
python3 bench/control-latency.py --runs 100 --baseline /path/to/old/dist/index.js

# Linux เท่านั้น: ขอใช้ไมค์ชั่วคราว ไม่บันทึกหรือส่งเสียง
node bench/mic-latency.mjs --allow-mic
npm test
```

อย่าใช้การถอดเสียงคนละประโยค/คนละช่วงเครือข่ายเพื่อสรุปผล optimization ควรเก็บก่อน/หลังด้วย fixture เดียวกันหลายความยาว (เช่น 1/3/10/30s) สลับลำดับ แยกภาษา และรายงาน error/empty/accuracy ควบคู่ latency การทดลอง API รอบนี้ยังไม่ได้ทำ และจะมีการส่งเสียง/ใช้ quota เมื่อทำจริง
